# AI ინტერვიუერი (v2) — Interview → Summary → Edit/Confirm → Central Storage → Manager View

პროტოტიპი, რომელიც ესაუბრება თანამშრომელს მისი სამუშაო პროცესების შესახებ, გამოავლენს რამდენიმე
დამოუკიდებელ **opportunity**-ს (გაუმჯობესების/ავტომატიზაციის/AI-ის შესაძლებლობებს), აძლევს
თანამშრომელს **გადახედვისა და რედაქტირების** საშუალებას თითოეულ ჩანაწერზე ცალკე, და
**დადასტურების** შემდეგ ინახავს მათ ცენტრალურ ბაზაში — საიდანაც **Manager View** კითხულობს ყველა
დეპარტამენტის დადასტურებულ შედეგებს ერთად.

**Backend**: Python (Flask) + SQLite. **Frontend**: ორი HTML ფაილი (`index.html` — ინტერვიუ + Review/Confirm,
`manager.html` — Manager View), თითოეული ჩაშენებული CSS/JS-ით.

## Flow, ეტაპობრივად

1. **Interview** — თანამშრომელი პასუხობს AI-ის კითხვებს (`/api/chat`, `static/index.html`).
2. **Summary** — "ანალიზის გენერირება" ღილაკზე დაჭერისას (`/api/summary`), Gemini-ს ეგზავნება მთელი
   ტრანსკრიპტი და უბრუნდება **მასივი** opportunity-ების, თითოეული 12 ველით (პროცესი, პრობლემა,
   სიხშირე, დროის დანახარჯი, კატეგორია, პრიორიტეტი და ა.შ.). ეს ინახება ბაზაში `status='draft'`-ით.
3. **Edit/Confirm** — თითოეული opportunity ჩნდება რედაქტირებად ბარათად. თანამშრომელს შეუძლია:
   - შეასწოროს ნებისმიერი ველი და დააჭიროს "შენახვა" (სტატუსი ხდება `edited`);
   - დააჭიროს "დადასტურება" (სტატუსი ხდება `confirmed`, ბარათი იკეტება რედაქტირებისთვის).
4. **Central Storage** — დადასტურებული ჩანაწერები ცხოვრობენ `opportunities` ცხრილში, დაკავშირებული
   შესაბამის `interviews` ჩანაწერთან (რომელიც სრულ ტრანსკრიპტს ინახავს).
5. **Manager View** (`/manager.html`) — ცხრილი ყველა დადასტურებული opportunity-სი, ყველა
   დეპარტამენტიდან ერთად, ფილტრებით (დეპარტამენტი/კატეგორია/პრიორიტეტი). ჩანაწერზე დაწკაპუნებით
   იხსნება სრული დეტალები + სრული საუბრის ტრანსკრიპტი.

## რატომ SQLite (და არა ცალკეული ფაილები ან სრული SQL სერვერი)

- **ჩაშენებულია Python-ში** — დამატებითი პაკეტის, სერვისის ან ანგარიშის შექმნა არ სჭირდება.
- **ნამდვილად ცენტრალურია** — ერთი ფაილი, საიდანაც Manager View-ს შეუძლია ყველა დეპარტამენტის
  მონაცემის ერთდროულად წაკითხვა/ფილტრაცია (რაც ცალკეული JSON ფაილებით შეუძლებელი იყო).
- **საკმარისია V1 პროტოტიპისთვის** — არ საჭიროებს ცალკე დატაბაზის სერვერს, connection string-ს, ან
  დამატებით environment variable-ს.

> **⚠️ Render-ის უფასო ტარიფის შეზღუდვა უცვლელია**: `data/app.db` ისეთივე ეფემერული დისკის
> შეზღუდვას ექვემდებარება, როგორც v1-ის JSON ფაილები — ის წაიშლება ყოველი redeploy-ის ან
> გადატვირთვისას. SQLite-ზე გადასვლა წყვეტს **ცენტრალიზაციის** ამოცანას, არა **მუდმივობის**
> ამოცანას. ნამდვილი production-ის მუდმივი შენახვისთვის (PostgreSQL ან ანალოგიური, Render-ის
> persistent disk-ით ან გარე managed database-ით) — იხ. "Production მზაობის ანალიზი" დოკუმენტი.

## Opportunity-ის ველების განმარტება

თითოეული opportunity, რომელსაც AI აგენერირებს, შედგება შემდეგი ველებისგან:

| ველი | რას ნიშნავს |
|---|---|
| `process` | რომელ პროცესს ეხება — მოკლე სახელი (მაგ. "CV-ების გადარჩევა") |
| `problem` | კონკრეტული პრობლემა, რაც თანამშრომელმა აღწერა |
| `current_method` | როგორ კეთდება ეს დღეს — ხელით თუ რომელი ხელსაწყოთი |
| `frequency` | რამდენად ხშირად მეორდება (მაგ. "თვეში ერთხელ") |
| `time_estimate` | სავარაუდო დროის დანახარჯი (მაგ. "~3 საათი") |
| `existing_tools` | რა ხელსაწყოებით/სისტემებით სარგებლობს ამჟამად (Excel, ელფოსტა და ა.შ.) |
| `main_difficulty` | მთავარი სირთულე/ბლოკერი ამ პროცესში |
| `desired_outcome` | რა შედეგი სურს თანამშრომელს საბოლოოდ |
| `solution_category` | გადაწყვეტის ტიპი — იხ. ცხრილი ქვემოთ |
| `ai_relevance` | მოკლედ, რატომ/როგორ დაეხმარება AI ამ კონკრეტულ საკითხს |
| `automation_relevance` | მოკლედ, რატომ/როგორ დაეხმარება ჩვეულებრივი ავტომატიზაცია |
| `priority` | პრიორიტეტი — განისაზღვრება სიხშირისა და დროის დანაკარგის მიხედვით |

თუ რომელიმე ველისთვის საუბარში ინფორმაცია არ მოიძებნა, AI წერს ზუსტად **"უცნობია"** — არასდროს იგონებს.

### `solution_category` — სამი შესაძლო მნიშვნელობა

AI თავად ირჩევს ერთ-ერთს, საუბრის შინაარსზე დაყრდნობით (იხ. `app.py` → `build_summary_system_prompt`):

| მნიშვნელობა | გამოჩნდება, როგორც | რას ნიშნავს |
|---|---|---|
| `improvement` | პროცესის გაუმჯობესება | პრობლემა, რომლის გადაწყვეტაც შესაძლებელია ტექნოლოგიის გარეშეც — მაგ. პროცესის თანმიმდევრობის შეცვლა, პასუხისმგებლობის გადანაწილება, კომუნიკაციის გამარტივება |
| `automation` | ავტომატიზაცია | წესებზე დაფუძნებული, გამეორებადი ამოცანა, რომლის ავტომატიზირება სკრიპტით/ინტეგრაციით/workflow-ით შესაძლებელია — მაგ. Excel ფაილების ავტომატური გაერთიანება, მონაცემების სინქრონიზაცია ორ სისტემას შორის |
| `ai` | AI-ს გამოყენება | ამოცანა, სადაც სჭირდება რაღაც "ჭკვიანი" — ტექსტის გენერაცია, კლასიფიკაცია, არასტრუქტურირებული მონაცემის ანალიზი — მაგ. CV-ების გადარჩევა |

### `priority` — სამი დონე

| მნიშვნელობა | გამოჩნდება, როგორც |
|---|---|
| `high` | მაღალი |
| `medium` | საშუალო |
| `low` | დაბალი |

## API როუტები

| როუტი | მეთოდი | დანიშნულება |
|---|---|---|
| `/` | GET | ინტერვიუს გვერდი |
| `/manager.html` | GET | Manager View გვერდი |
| `/api/chat` | POST | ერთი საუბრის ტური |
| `/api/summary` | POST | ტრანსკრიპტიდან draft opportunities-ის გენერირება + ბაზაში ჩაწერა |
| `/api/opportunities/<id>` | GET | ერთი opportunity + სრული ინტერვიუს ტრანსკრიპტი |
| `/api/opportunities/<id>` | PUT | ველების განახლება და/ან დადასტურება (`confirm: true`) |
| `/api/opportunities?status=confirmed` | GET | ყველა დადასტურებული opportunity (Manager View-სთვის) |
| `/api/health` | GET | სერვერის სტატუსი |

## ლოკალურად გაშვება

იგივეა, რაც v1-ში:

```bash
python3 -m venv venv
source venv/bin/activate        # Windows-ზე: venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env            # და ჩაწერეთ თქვენი GEMINI_API_KEY
python app.py
```

გახსენით:
- **http://localhost:3000** — ინტერვიუსთვის
- **http://localhost:3000/manager.html** — Manager View-სთვის

ბაზა (`data/app.db`) ავტომატურად იქმნება პირველივე გაშვებისას.

## უსაფრთხოება — მნიშვნელოვანი შენიშვნა Manager View-ზე

**Manager View ამ ეტაპზე დაცული არ არის** — ნებისმიერს, ვინც `/manager.html` URL-ს იცის, შეუძლია
ნახოს ყველა თანამშრომლის დადასტურებული პასუხი (და, ჩანაწერზე დაწკაპუნებით, სრული საუბრის
ტრანსკრიპტიც). ეს განზრახ არის გამარტივებული ამ პროტოტიპში — ავტორიზაცია/წვდომის კონტროლი
სხვა დეველოპერის საქმეა production-ზე გადასვლისას (იხ. "Production მზაობის ანალიზი").

**რჩევა handoff-ისთვის**: თანამშრომლებმა წინასწარ უნდა იცოდნენ, რომ მათი დადასტურებული პასუხები
(არა მხოლოდ აგრეგირებული სტატისტიკა) ხილვადი იქნება Manager View-ში — ეს პოლიტიკის საკითხია,
რომელიც უნდა გადაწყდეს ტექნიკურ დანერგვამდე.

## ცნობილი შეზღუდვები (ეს ისევ პროტოტიპია)

- `data/app.db` ეფემერულია Render-ის უფასო ტარიფზე (იხ. ზემოთ).
- Manager View დაცული არ არის ავტორიზაციით.
- არ არსებობს "draft" ან "edited" (მაგრამ არა confirmed) ჩანაწერების სია — მხოლოდ confirmed ჩანს
  Manager View-ში; დაუდასტურებელი ჩანაწერები მხოლოდ იმ თანამშრომლისთვისაა ხილული, ვინც შექმნა
  (და მხოლოდ იმავე ბრაუზერის სესიაში, `localStorage`-ის წყალობით).
- API-ის გამოძახებებზე rate limiting არ არის კონფიგურირებული.
- არ არის ავტომატური ტესტები.

დეტალური სია იხილეთ ცალკე დოკუმენტში: **"Production მზაობის ანალიზი"**.
